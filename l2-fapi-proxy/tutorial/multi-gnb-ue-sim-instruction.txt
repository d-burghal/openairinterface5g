================================================================================
  Multi-gNB / Multi-UE OAI 5G L2 Proxy Simulation — Tutorial & Instructions
================================================================================

This document provides a complete, step-by-step guide for setting up and running
an OAI 5G simulation with multiple gNBs and multiple UEs using the L2 Proxy
layer (no radio hardware required).



================================================================================
  Quick Start (TL;DR)
================================================================================

If you already have images built and the core network running, the full
simulation workflow is:

  # --- On the HOST machine ---
  cd <your-workspace-path>/oai-ran/tutorial

  # 1. Deploy gNBs (e.g., 3 gNBs)
  ./scripts/start_gnb_pods.sh -c 3

  # 2. Deploy UEs via Helm (e.g., 10 UEs)
  cd <your-workspace-path>/oai-cn5g-fed
  helm install nr-ue-multi oai-5g-ran/oai-nr-ue-multi -n oai

  # --- Inside the gNB-00 container ---
  kubectl exec -it <gNB-00-pod> -n oai -- /bin/bash
  cd /opt/oai-ran/l2-fapi-proxy && make
  cd /opt/oai-ran/l2-fapi-proxy && ./src/run_l2_proxy.sh 3 10

  # (new terminal, same container)
  cd /opt/oai-ran/cmake_targets/ran_build/build
  ./nr-softmodem -O /tmp/gnb.conf --nfapi VNF

  # --- Back on the HOST machine ---
  cd <your-workspace-path>/oai-ran/tutorial

  # 3. Start UEs (e.g., UE indices 0–9)
  ./scripts/run_ue_oai.sh 0 9

  # 4. Start iperf traffic (downlink)
  ./scripts/start_ue_iperf.sh 0 9

  # 5. When done — stop traffic and UEs
  ./scripts/stop_ue_iperf.sh 0 9
  ./scripts/stop_ue_oai.sh 0 9


================================================================================
  Important: Path Mapping & Directory Layout
================================================================================

Understanding how host paths map to container paths is critical.

  HOST PATH                                    CONTAINER PATH
  -------------------------------------------  ---------------------------
  <your-workspace-path>/oai-ran/              /opt/oai-ran/
  <your-workspace-path>/oai-cn5g-fed/          /opt/oai-gnb/  (gNB configs)

  Key subdirectories inside the gNB container:
    /opt/oai-ran/l2-fapi-proxy/               L2 proxy source & build
    /opt/oai-ran/cmake_targets/ran_build/build/  Softmodem executables
    /opt/oai-gnb/etc/gnb.conf                 Base gNB config (from ConfigMap)
    /tmp/gnb.conf                             Final gNB config (auto-generated)

  Key paths inside UE containers:
    /opt/oai-nr-ue/                            UE binaries & configs
    /opt/oai-nr-ue/etc/run_ue_l2proxy.sh       UE startup script (L2 proxy mode)
    /opt/oai-nr-ue/etc/stop_ue.sh              UE stop script

  NOTE: The host RAN repository is volume-mounted into the gNB container at
  /opt/oai-ran. Any file you edit on the host (e.g., l2-fapi-proxy/) is
  immediately visible inside the container — no rebuild of the image needed
  for source code changes, just recompile inside the container.

  NOTE: The tutorial/ directory in this repo contains helper scripts and the
  trace generator. These scripts run on the HOST machine (they use kubectl to
  interact with pods). They do NOT run inside containers.

================================================================================
  Phase 4: gNB Deployment
================================================================================

This phase uses the `start_gnb_pods.sh` script from the tutorial/scripts/ directory.

--- 4.1 Script: start_gnb_pods.sh ---

  WHERE TO RUN: Host machine (uses kubectl/helm to interact with K8s)

  Arguments:
    -n, --namespace NAME    Kubernetes namespace (default: auto-detected, prefers "oai")
    -c, --num-gnb NUM        Number of gNBs to deploy (default: from values.yaml)
    <positional number>      Same as -c (e.g., ./start_gnb_pods.sh 3)
    -h, --help               Show help

  What it does (step by step):
    1. Checks prerequisites (kubectl, helm, charts directory exist)
    2. Auto-selects namespace (prefers "oai", falls back to "default")
    3. Updates values.yaml gnbIds array with the requested gNB count
       (e.g., 3 gNBs → gnbIds: ["00", "01", "02"])
    4. Cleans any existing oai-gnb-multi Helm release (uninstall + force-delete pods)
    5. Runs: helm install oai-gnb-multi oai-5g-ran/oai-gnb-multi -n <namespace>
    6. Waits up to 300 seconds for all gNB pods to reach 1/1 Ready state
    7. FIXES L2 PROXY IPs:
       a. Finds gNB-00 pod and gets its IP address
       b. Gives gNB-00 a 5-second head start
       c. For EVERY gNB pod, runs sed on /tmp/gnb.conf to set:
          - local_s_if_name  = "eth0"        (was "lo:")
          - remote_s_address = "<gNB-00-IP>" (was "127.0.0.1")
          - local_s_address  = "<pod's-own-IP>" (was "127.0.0.2")
       This ensures all gNBs connect to the L2 proxy server running on gNB-00.
    8. Verifies configurations (runs check_all_gnb_configs.sh if available,
       else does manual grep of remote_s_address in /tmp/gnb.conf)

  Example usage:
    cd <your-workspace-path>/oai-ran/tutorial
    ./scripts/start_gnb_pods.sh -c 3          # Deploy 3 gNBs to "oai" namespace
    ./scripts/start_gnb_pods.sh -n test -c 5  # Deploy 5 gNBs to "test" namespace
    ./scripts/start_gnb_pods.sh 4              # Deploy 4 gNBs (positional arg)

  What to expect:
    - Colored log output showing each phase
    - All pods reach 1/1 Ready
    - "Enhanced gNB deployment completed successfully!" message
    - gNB pods are deployed but NOT yet running softmodem (they sleep infinity)

================================================================================
  Phase 6: Build L2 Proxy & gNB Softmodem
================================================================================

--- 6.1 Enter the gNB Container ---

  WHERE TO RUN: Host machine (to exec into container)

  # Find the gNB-00 pod name
  kubectl get pods -n oai | grep oai-gnb

  # Enter the gNB-00 container
  kubectl exec -it <GNB_00_POD_NAME> -n oai -- /bin/bash

  NOTE: You are now INSIDE the gNB container. The host path
  <your-workspace-path>/oai-ran/ is mounted at /opt/oai-ran/ inside.

--- 6.2 Build the L2 Proxy ---

  WHERE TO RUN: Inside gNB container

  cd /opt/oai-ran/l2-fapi-proxy
  make

  # The proxy binary will be at:
  # /opt/oai-ran/l2-fapi-proxy/build/proxy

--- 6.3 Build gNB Softmodem (First Time) ---

  WHERE TO RUN: Inside gNB container

  cd /opt/oai-ran
  source oaienv
  cd cmake_targets
  mkdir -p log
  ./build_oai -I --install-optional-packages

  # Full build with debug:
  ./build_oai -c -g Debug --ninja \
    --gNB --RU --nrUE \
    --build-lib "telnetsrv uescope nrscope" \
    -t Ethernet \
    --noavx512 \
    --build-tool-opt -k10 \
    --cmake-opt -DCMAKE_C_FLAGS="-Werror" --cmake-opt -DCMAKE_CXX_FLAGS="-Werror"

  # Verify executables
  ldd ran_build/build/*softmodem* ran_build/build/nr-cuup ran_build/build/oairu

  NOTE: -g Debug gives maximum debug output. Remove it for production builds.

  Resulting executables are in /opt/oai-ran/cmake_targets/ran_build/build/:
    - nr-softmodem      (gNB executable)
    - nr-cuup           (CU-UP executable)
    - oairu              (Radio Unit executable)
    - nr-uesoftmodem    (NR UE executable)

--- 6.4 Subsequent (Incremental) Builds ---

  WHERE TO RUN: Inside gNB container

  cd /opt/oai-ran/cmake_targets/ran_build/build
  cmake --build . --target nr-softmodem nr-cuup oairu nr-uesoftmodem \
    telnetsrv uescope nrscope oai_eth_transpro params_libconfig coding \
    rfsimulator dfts params_yaml vrtsim -- -j48 -k10

  # Rebuild L2 Proxy only
  cd /opt/oai-ran/l2-fapi-proxy
  make

================================================================================
  Phase 8: Start UEs
================================================================================

--- 8.1 Script: run_ue_oai.sh ---

  WHERE TO RUN: Host machine

  Arguments:
    run_ue_oai.sh <START_UE_IDX> <END_UE_IDX>

  What it does (step by step):
    1. Gets all oai-nr-ue-multi pod names via kubectl
    2. For each UE index in the range [START_UE_IDX, END_UE_IDX]:
       a. Selects the corresponding pod from the list
       b. Runs: kubectl exec -n oai <POD> -- bash /opt/oai-nr-ue/etc/run_ue_l2proxy.sh
          (in background, so UEs start in parallel)
       c. Sleeps 0.5 seconds between UEs to stagger startup

  The script run_ue_l2proxy.sh inside the UE container starts the
  nr-uesoftmodem in L2 proxy mode, connecting to the proxy server on gNB-00.

  Example usage:
    cd <your-workspace-path>/oai-ran/tutorial
    ./scripts/run_ue_oai.sh 0 9    # Start UEs 0 through 9 (10 UEs)
    ./scripts/run_ue_oai.sh 0 0    # Start only UE 0

  What to expect:
    - Each UE will perform cell selection, SIB1 decode, and random access
    - Look for "4-Step RA procedure succeeded" in UE logs
    - UEs should connect to the gNB determined by the channel trace


================================================================================
  Phase 9: Generate Channel Traces
================================================================================

The L2 proxy uses a channel trace CSV to simulate radio conditions and control
which gNB each UE connects to. The trace generator is included in the tutorial
directory.

--- 9.1 generate_dedicated_trace.py (in tutorial/) ---

  WHERE TO RUN: Host machine (generate the CSV, then reference it when
  starting the L2 proxy)

  This script generates a channel trace CSV with deterministic UE→gNB mapping.
  Each UE is assigned to exactly one gNB. The target gNB gets a strong RSRP
  (-50 dBm) while all other gNBs get a weak RSRP (-140 dBm).

  Output format (8 fields, matches the proxy parser):
    UE_ID,Trace_Index,RSSI_dBm,SINR_dB,RSRP_dBm,gnb_id,time_index,gnb_name

  Usage:
    cd <your-workspace-path>/oai-ran/tutorial
    python3 generate_dedicated_trace.py --num-ue 10 --num-gnb 3 -o channel_trace.csv

  Arguments:
    --output, -o            Output CSV file (default: channel_trace.csv)
    --num-ue, -u            Number of UEs (default: 4)
    --num-gnb, -g           Number of gNBs (default: 2, max: 8)
    --num-iterations, -n    Trace rows per UE per gNB (default: 100)
    --strong-rsrp           RSRP for target gNB in dBm (default: -50)
    --weak-rsrp             RSRP for non-target gNBs in dBm (default: -140)
    --strong-sinr          SINR for target gNB in dB (default: 30)
    --weak-sinr            SINR for non-target gNBs in dB (default: -10)
    --no-header             Omit CSV header line

  UE→gNB mapping: UE0→gNB0, UE1→gNB1, ... wraps around.
  Example: 10 UEs, 3 gNBs → UE0→gNB0, UE1→gNB1, UE2→gNB2, UE3→gNB0, ...

  To use the trace with the L2 proxy:
    # Inside gNB-00 container:
    cd /opt/oai-ran/l2-fapi-proxy
    ./src/run_l2_proxy.sh 3 10 /opt/oai-ran/tutorial/channel_trace.csv

  NOTE: The trace file path must be accessible inside the container. Since the
  host repo is mounted at /opt/oai-ran, placing the CSV in the tutorial/
  directory makes it available at /opt/oai-ran/tutorial/channel_trace.csv.


================================================================================
  Phase 10: Start Traffic (iperf3)
================================================================================

--- 10.1 Script: start_ue_iperf.sh ---

  WHERE TO RUN: Host machine

  Arguments:
    start_ue_iperf.sh <START_UE_IDX> <END_UE_IDX>

  What it does (step by step):
    1. Finds the oai-traffic-server pod and gets its internal IP
    2. Finds the oai-upf pod and gets its internal IP
    3. On the traffic server pod:
       a. Adds route: 12.1.1.0/24 via <UPF_IP> dev eth0
          (so the traffic server can reach the UE DNN subnet)
       b. Assigns DNN IP: 12.1.2.1/24 to eth0
          (the traffic server's IP on the DNN subnet)
    4. On the UPF pod:
       a. Adds route: 12.1.2.0/24 dev eth0
          (so UPF forwards traffic-server subnet to the right interface)
    5. For each UE in range [START_UE_IDX, END_UE_IDX]:
       a. Adds route on UE pod: 12.1.2.0/24 dev oaitun_ue1
          (so UE can reach the traffic server's DNN IP)
    6. For each UE in range:
       a. Extracts UE ID from pod name (e.g., oai-nr-ue-multi-5 → UE_ID=5)
       b. Computes iperf port: 52<UE_ID> (e.g., UE 5 → port 525)
       c. Runs: iperf3 -c 12.1.2.1 -p 52<UE_ID> -b 1M -R -t 0 --logfile /tmp/iperf.log
          (in background)
          -R  = reverse mode (downlink: server → UE)
          -b 1M = 1 Mbps bandwidth
          -t 0 = unlimited duration

  Network topology:
    UE (12.1.1.x) → oaitun_ue1 → UPF → traffic-server (12.1.2.1)

  Example usage:
    cd <your-workspace-path>/oai-ran/tutorial
    ./scripts/start_ue_iperf.sh 0 9    # Start iperf on UEs 0–9

  What to expect:
    - "Traffic server pod: ..." and IP addresses printed
    - "Configuring traffic server DNN IP and routes..."
    - "Connecting UE <ID> iperf client to traffic server 12.1.2.1 port 52<ID>..."
    - iperf runs in background, logs to /tmp/iperf.log inside each UE pod

  To check iperf results:
    kubectl exec -n oai <UE_POD> -- cat /tmp/iperf.log

================================================================================
  How /tmp/gnb.conf Gets Created
================================================================================

The /tmp/gnb.conf file is the final gNB configuration used by nr-softmodem.
It is generated automatically during container startup.

--- Step 1: Helm Chart Deployment ---

When you run start_gnb_pods.sh (or helm install manually), the Helm chart:
  1. Creates a ConfigMap for each gNB instance from configmap.yaml
     (contains base gNB config with MCC, MNC, TAC, cell IDs, etc.)
  2. Creates an auto-config ConfigMap from auto-config-configmap.yaml
     (contains the auto-configuration script)
  3. Mounts the base config to /opt/oai-gnb/etc/gnb.conf inside the container
  4. Mounts the auto-config script to /tmp/auto-config.sh

--- Step 2: Container Initialization (Runtime) ---

When the container starts, /tmp/auto-config.sh runs and performs:

  1. Basic Network Configuration:
     - Resolves AMF IP address (DNS or fallback to hostname)
     - Gets container's N2/N3 interface IP addresses
     - Uses sed to replace placeholders in the config:
       @N2_IP_ADDRESS@, @N3_IP_ADDRESS@, @AMF_IP_ADDRESS@
     - Copies result to /tmp/gnb.conf

  2. Enhanced MACRLC Configuration (L2 Proxy):
     - Discovers the current gNB's IP: GNB_IP=$(ip addr show eth0 ...)
     - Extracts gNB ID from hostname
     - For gNB 00: Sets L2_PROXY_IP to its own IP (it IS the proxy server)
     - For other gNBs: Discovers gNB 00's IP via:
       a. DNS: getent hosts oai-gnb-00
       b. Ping: ping -c 1 oai-gnb-00
       c. IP scanning fallback
     - Updates /tmp/gnb.conf MACRLC parameters:
       local_s_if_name  = "eth0"           (was "lo:")
       remote_s_address = "<gNB-00-IP>"     (was "127.0.0.1")
       local_s_address  = "<this-gNB-IP>"   (was "127.0.0.2")

  3. Container Management:
     - Either starts gNB softmodem or keeps container running with sleep infinity
       (based on Helm chart start.gnb config value)

--- Step 3: Manual Execution ---

When you manually run:
  ./nr-softmodem -O /tmp/gnb.conf --nfapi VNF

The /tmp/gnb.conf is already there from the auto-configuration process,
containing all the correct network and L2 proxy IP settings.

--- Additional L2 Proxy IP Fix (by start_gnb_pods.sh) ---

After pods are ready, start_gnb_pods.sh also runs sed commands on /tmp/gnb.conf
for every gNB pod to ensure the L2 proxy IPs are correct. This is a belt-and-
suspenders approach in case auto-config.sh didn't fully work.

================================================================================
  Alternative: RFSIM Mode
================================================================================

If you want to run with RFSIM instead of L2 Proxy (no proxy layer, uses
RF simulator for over-the-air simulation):

  For gNB (inside gNB container):
    ./nr-softmodem -O /tmp/gnb.conf --sa --rfsim

  For UE (inside UE container):
    /opt/oai-nr-ue/bin/nr-uesoftmodem \
        -O /opt/oai-nr-ue/etc/nr-ue.conf \
        --rfsimulator.serveraddr $RFSIM_IP_ADDRESS

  NOTE: RFSIM mode does not use the L2 proxy or channel traces. It simulates
  the air interface directly. This is simpler but does not support multi-gNB
  cell selection based on channel traces.
